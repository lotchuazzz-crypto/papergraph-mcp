# v1.1.1 Evidence Triage / First-Reading Usability Design

## Context

PaperGraph v1.1.0 added Workspace Starter and Reading Project Bootstrap on top of the stable v1 evidence-first core. A first-use simulation on a local PDF showed that the tool already preserves the right evidence boundaries: it loaded the paper, extracted theorem-like records, avoided guessing external paper identities, reported sparse local dependency evidence, and warned that empty dependency results are scoped extraction results rather than mathematical facts.

The same simulation also exposed the next usability gap. When only one local dependency edge was extracted, the generated user-facing summary still required a careful human or agent to interpret the situation. A first-time user needs a clearer triage layer:

- what PaperGraph extracted confidently;
- what was missing or truncated;
- what is safe to read next;
- what is only an automatic candidate;
- what external references need user action;
- what commands or files continue the workflow.

v1.1.1 should complete the v1.1 usability story without expanding PaperGraph's mathematical claims.

## Product Goal

PaperGraph v1.1.1 should make sparse or incomplete extraction results easy to act on. Reading Reports and Starter summaries should present a deterministic Evidence Triage section that separates supported local evidence, extraction limits, candidate-only guidance, external import blockers, and concrete next actions.

The release remains a usability hardening release. It must not add semantic theorem matching, proof verification, hidden dependency inference, global literature discovery, or LLM-authored mathematical judgment.

## Users

- A first-time researcher loading one PDF or one local paper.
- An agent using PaperGraph to produce a reading handoff for a user.
- A maintainer reviewing whether a sparse dependency graph is a bug, an extraction limit, or expected evidence-boundary behavior.

## Design Principles

- **Triage before interpretation:** Give the user a status diagnosis before showing long tables or route details.
- **Evidence labels everywhere:** Distinguish supported edges, unresolved references, candidate starts, missing proofs, proof fragments, and blocked external imports.
- **No false negatives:** Empty dependency results must remain scoped to PaperGraph's extraction basis.
- **No false positives:** Candidate starts and cited-result mentions must not be presented as logical dependency edges.
- **Reuse existing data:** Build from Paper Map, Reading Report, dependency diagnostics, external import plans, and starter warnings.
- **Deterministic artifacts:** No timestamps, random IDs, or environment-derived facts beyond user-supplied paths.

## Approaches Considered

### Option 1: Documentation-Only Wording Pass

Update README, walkthroughs, and report prose to explain sparse dependency output more clearly.

This is safe but insufficient. The user's first artifact still has to assemble meaning from several sections. It also gives agents no structured object to inspect.

### Option 2: Improve Extraction Heuristics

Add more regexes or parser logic to extract additional proof dependencies and citation targets.

This could improve some papers, but it does not solve the product problem. Sparse extraction will always happen for difficult PDFs, missing proofs, OCR issues, bibliography gaps, or unsupported wording. v1.1.1 should first make sparse results usable.

### Option 3: First-Class Evidence Triage Layer

Add a small deterministic triage model that summarizes current evidence quality, dependency coverage, candidate confidence, external blockers, and recommended next actions. Reading Report and Starter render it near the top, and MCP/CLI expose it through existing or new report payload fields.

This is the recommended route. It makes the current system more understandable without changing extraction semantics.

## Scope

### In Scope

Add a deterministic triage layer that:

- classifies every paper into a small first-use status:
  - `usable_with_cautions`;
  - `sparse_dependencies`;
  - `proofs_missing_or_fragmentary`;
  - `external_blocked`;
  - `needs_manual_review`;
- summarizes theorem-like extraction counts by kind;
- reports local dependency evidence count and the strongest supported local dependency chain when available;
- explicitly labels automatic start results as `candidate_starting_point`;
- lists missing proof evidence and proof-fragment-only results as extraction limits;
- summarizes external import candidates and blockers with user-action language;
- emits concrete next actions with command/file references;
- renders the triage in Reading Reports and `START_HERE.md`;
- stores the triage object in JSON payloads and starter manifest;
- updates docs and examples so first-time users see triage-first output.

### Out of Scope

- New theorem/proof extraction logic.
- New database schema.
- New paper discovery.
- Automatic bibliography lookup.
- Automatic external paper import.
- Ranking the "main theorem" by mathematical importance.
- Claiming that missing dependencies imply mathematical independence.
- LLM-generated mathematical explanation.

Add an internal triage model:

```python
    },

    ],
    "candidate_starting_point": {

            "citation_key": "17",

```

The model may be assembled from existing `paper_map`, `workspace.get_dependencies(...)`, `workspace.get_dependency_diagnostics(...)`, and `workspace.plan_external_imports_for_paper(...)` outputs. It should not query network services.

## Reading Report Changes

Every Reading Report should place this section immediately after `## Paper Map`:

```markdown
## Evidence Triage

- Status: `sparse_dependencies`
- Headline: Local dependency evidence is sparse; use this report as a review map, not a complete dependency graph.
- Supported local dependency chains: 1
- External import blockers: 2
- Candidate starting point: `local:paper::corollary:2.7` (automatic candidate, not a main-theorem claim)

### What Is Safe To Use

- PaperGraph found one supported local dependency edge: `Lemma 4.3 -> Lemma 2.6`.

### What Needs Review

- Several theorem-like results have no supported proof/dependency evidence.
- Empty dependency results do not imply mathematical independence.

### Next Actions

1. Read Lemma 2.6 before Lemma 4.3.
2. Review theorem statements whose proofs were missing or fragmentary.
3. Resolve blocked citations `[17]` and `[3]` before importing external papers.
```

Existing sections remain, but their wording should use triage terms:

- `Recommended start result` becomes `Candidate starting point`.
- `Recommended Reading Route` becomes `Candidate Reading Route` when evidence is sparse.
- `Local Logic Chain` should say `Supported Local Logic Chain`.
- If no local dependency evidence exists, the section should lead with the extraction-boundary explanation rather than a bare negative result.

## Starter Summary Changes

`START_HERE.md` should promote the triage summary into `## Start Here`:

- for usable local evidence, name the first supported chain;
- for sparse dependencies, say that the starter package is a review map;
- for external blockers, list the blocked citation keys and required user inputs;
- for missing proof evidence, point the user to the Reading Report's Evidence Triage section.

The starter manifest should include:

```json
{
  "evidence_triage": [
    {
      "paper_id": "local:kiem-moon",
      "status": "sparse_dependencies",
      "local_dependency_edge_count": 1,
      "external_blocked_count": 2,
      "next_actions": [...]
    }
  ]
}
```

## MCP / CLI Surface

No new command is required for v1.1.1. The triage should ride inside existing report and starter payloads:

- `workspace_export_paper_reading_report` returns `evidence_triage`;
- `export-paper-reading-report` writes Markdown containing `## Evidence Triage`;
- `workspace_bootstrap_reading_project` returns per-paper triage in the payload;
- `bootstrap-reading-project` writes triage into `START_HERE.md` and `papergraph-starter-manifest.json`.

Optional follow-up if implementation stays small:

```python
workspace_get_evidence_triage(paper_id: str, max_candidates: int = 5) -> dict
```

This optional tool should be added only if tests show callers need triage without exporting a full report.

## Architecture

Create:

```text
src/papergraph/evidence_triage.py
```

Responsibilities:

- build triage payloads from an existing `Workspace` and `paper_id`;
- consume existing Paper Map and external import planner outputs;
- derive counts and status labels;
- collect supported local dependency chains from existing route/dependency data;
- convert blocked external imports into user-action messages;
- render triage Markdown snippets for Reading Report and Starter.

Modify:

```text
src/papergraph/reading_report.py
src/papergraph/starter.py
src/papergraph/server.py
tests/
docs/
```

`reading_report.py` should not grow a large new analyzer. It should call `build_evidence_triage(...)` and render the returned model.

`starter.py` should reuse the same model from Reading Report payloads where possible, rather than recomputing independently.

## Status Classification

Apply statuses in this order:

1. `external_blocked` when there are blocked external import items and no importable candidate resolves them.
2. `proofs_missing_or_fragmentary` when many high-ranked candidates or theorem-like results lack proof evidence.
3. `sparse_dependencies` when theorem-like results exist but supported local dependency edges are below a small threshold.
4. `usable_with_cautions` when there is at least one supported local chain or usable Paper Map candidate and no dominant blocker.
5. `needs_manual_review` as the fallback for unusual or contradictory payloads.

Thresholds must be deterministic and conservative. The first implementation may use simple counts:

- sparse when theorem-like count is at least 3 and local dependency edge count is 0 or 1;
- fragmentary when evidence-quality warnings include sparse proof/proof missing indicators;
- external blocked when `external_risks.summary.blocked_count > 0`.

The status is not a quality score and must not be rendered as a mathematical confidence measure.

## Error Handling

- If Paper Map generation fails, triage returns `needs_manual_review` with an extraction-limit entry and does not hide the original error.
- If external import planning fails, triage still renders local evidence and adds an external-planning warning.
- If dependency diagnostics are unavailable for a result, triage treats that result as unreviewed rather than dependency-free.
- Duplicate or malformed evidence records should not crash Markdown rendering; they should appear under extraction limits.

## Tests

Add focused tests for:

- triage model reports sparse dependencies when one local edge is found among several theorem-like records;
- empty dependencies render the scoped negative-result warning;
- candidate starting point is labeled as automatic candidate, not recommendation;
- blocked external imports render citation keys, location, reason, and next action;
- Reading Report includes `## Evidence Triage` before detailed route sections;
- Starter summary includes triage in `## Start Here`;
- starter manifest includes compact triage payloads;
- no triage output claims proof verification, semantic theorem matching, hidden dependency inference, or mathematical independence;
- existing v1.1 starter tests still pass.

## Release Notes Shape

Release as `v1.1.1`.

Release notes should emphasize:

- first-use Evidence Triage in Reading Reports and Starter artifacts;
- clearer handling of sparse dependency extraction;
- candidate-start labels that avoid main-theorem claims;
- external blocker next actions;
- unchanged v1 evidence boundaries.

They should avoid claiming improved theorem extraction, automatic bibliography recovery, proof verification, or complete dependency graphs.

## Acceptance Criteria

v1.1.1 is ready when:

- Reading Reports start with a clear Evidence Triage section after Paper Map;
- Starter artifacts tell a first-time user what to do next even when dependencies are sparse;
- candidate starts are not rendered as mathematical recommendations;
- blocked external imports include concrete user actions;
- triage data is available in report/starter JSON payloads;
- examples and onboarding docs teach triage-first interpretation;
- focused tests and the full deterministic suite pass;
- the release is tagged and published as `v1.1.1`.

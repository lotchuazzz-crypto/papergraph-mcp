# PaperGraph v1.1.5: Reference Resolver Quality and Explainable Matching

Date: 2026-09-23
Status: User approved on 2026-09-23; implemented locally, pending authorized CI/release
Baseline: v1.1.4, released at `f238c001d31384332349c1512599e33739f74109`

## 1. Goal

Make reference searches more accurate, conservative and explainable before
bounded expansion acts on their results. A reader must be able to distinguish
“this record has a DOI” from “this DOI matches the cited work”, understand
conflicts, and see the next action needed to unblock a reference.

The roadmap put resolver-quality hardening after reproducible fixtures.
v1.1.4 also brought bounded expansion forward. This release improves the
identity evidence consumed by that workflow, not its acquisition authority.

## 2. Approach and scope

Options considered:

1. **Conservative deterministic resolver hardening — recommended.** Improve
   query parsing, identity normalization, grouping and explanations together,
   with offline regression fixtures and explicit version boundaries.
2. Presentation-only improvements. Smaller, but retain misleading confidence
   and incorrectly split or merged identities.
3. New providers, model-based matching or a general bibliography parser.
   Broader coverage, but too much new uncertainty and operational scope here.

Included:

- Evidence-preserving bibliography hints for supported common citation forms.
- Shared DOI/arXiv normalization and conflict-aware candidate grouping.
- Versioned matching assessment, provider outcomes and actionable boundaries.
- Persistence and rendering through existing Workspace, CLI and MCP surfaces.
- Safe interaction with old search snapshots and expansion policy versions.
- A deterministic, reusable quality regression corpus.

Excluded: new providers; arbitrary PDF downloading; publisher scraping;
automatic overwrite; unattended scheduling; LLM/embedding matching; a complete
BibTeX/LaTeX parser; OCR correction; theorem matching; proof verification;
reading-project remediation task management; claims of real-client compatibility
without separately recorded runs. No new runtime dependency is required.

## 3. Current implementation constraints

- `reference_search.py` currently extracts hints by splitting punctuation,
  normalizes matching text to ASCII, gives score for identifier presence, and
  can assign `strong` from provider agreement alone.
- Candidate merge keys prioritize DOI, then arXiv, then title/author/year.
  Fields are filled from the first nonempty value; conflicting alternatives
  are not exposed as a structured assessment.
- `reference_expansion_policy.py` adds a separate conservative authorization
  check. Search confidence must remain distinct from import permission.
- Search snapshots and candidate IDs persist across refreshes. Workspace
  readers currently reconstruct schema version 1 and store candidate evidence
  as a list of strings. New assessments need real persistence, not rendering-
  time recalculation from changed algorithms.
- `workspace.py` is large. New pure parsing/identity/assessment logic belongs
  in focused modules, with thin storage and public-method integration.

## 4. Query extraction contract

Keep existing query keys. Add `query_schema_version: 2`, `parser_version`,
`identifier_hints`, `field_evidence` and `parse_warnings` for new searches.

Each field-evidence entry records field, extracted value, source evidence ID
when available, original text excerpt, extraction rule, and confidence
`explicit` or `heuristic`. Raw bibliography and citation text remain unchanged.
Missing fields stay absent/null; do not invent authors or publication years.

Support these bounded forms through explicit fixtures:

- Author initials/full names followed by a quoted or clearly delimited title.
- Titles marked by common TeX emphasis wrappers, including nested braces.
- Author-year forms and numbered bibliography prefixes.
- Titles longer than twelve words, Unicode names and mathematical TeX tokens.
- Explicit DOI/arXiv identifiers and their recognized URL forms.

Do not treat initials as sentence endings. Prefer unambiguous explicit title
delimiters; if multiple competing spans remain, leave the title hint unset
and return `uncertain_title`. Preserve unsupported TeX tokens rather than
executing or guessing them. Matching text uses Unicode normalization and
case folding; it must not drop mathematical tokens or all non-Latin letters.
Multiple plausible years yield `conflicting_years`, not the first year found.
Citation keys are fallback search text, never identity evidence.

## 5. Canonical identity and grouping

Use one identity helper for new searches, assessments and v2 expansion checks.
Do not replace historic IDs or rewrite stored records.

DOI normalization accepts bare DOI, `doi:` and recognized doi.org URL forms,
trims surrounding whitespace and wrappers, case-folds identity, and preserves
raw input. URL decoding occurs once for recognized resolver URLs only. Do not
strip meaningful balanced parentheses or suffix characters. Ambiguous trailing
punctuation produces a warning and cannot establish an exact identifier match.
Invalid identifiers are retained as raw evidence but excluded from identity.

arXiv normalization reuses the existing validated modern/legacy ID parser.
Store versionless work identity separately from an explicit `vN` version.
Embedded and separate version values must agree. Different explicit versions
may refer to the same work, but produce `version_conflict` and cannot silently
select the newest version. An unversioned reference does not manufacture a
version constraint.

Group records only on a shared valid DOI or versionless arXiv identity.
A record explicitly containing both can establish a cross-identifier link;
matching title alone cannot establish that link. A connected component with
multiple distinct DOIs or arXiv work IDs is marked `identifier_conflict`, not
flattened into an importable target. All member records and field alternatives
remain visible. Metadata-only records are deduplicated only when normalized
title, ordered authors and year all agree and are nonempty; empty records never
collapse into a common empty-key candidate.

Conflicting components have no synthesized acquisition target. Manual review
must select an unambiguous source record or supply an explicit target through
the existing resolution workflow. Never combine one record's title with an
unproven DOI/arXiv pair to produce apparent certainty.

Grouping, canonical display selection, warnings and ranking are invariant to
provider and record iteration order. Duplicate records from one provider count
once. Multiple provider names are corroboration, not proof of independence.

## 6. Matching assessment and ranking

New snapshots use `search_schema_version: 2`, `candidate_schema_version: 2`
and `resolver_version: deterministic_v2`. Preserve existing candidate fields
and enum values. Add a persisted `assessment` object containing:

- `identity_status`: `exact_identifier`, `corroborated_metadata`,
  `partial_match`, `insufficient_evidence` or `conflict`.
- `matched_fields`, `missing_fields`, `conflicts`, with source attribution.
- `reason_codes`: stable machine-readable strings.
- `source_status`: `arxiv_importable`, `metadata_only` or `review_required`.
- `auto_selection`: eligibility and reason codes under `unique_strong_v2`.

Field evidence distinguishes exact, normalized-equivalent, fuzzy, missing and
conflicting values. Identifier presence alone contributes no match evidence.
Provider agreement alone cannot produce `strong`.

Confidence rules, in precedence order:

1. Identity/version conflicts or competing strong identities: `ambiguous`.
2. Exact source identifier, with no known contradictory field evidence:
   `strong`.
3. Exact normalized title, compatible nonempty author evidence, matching
   unambiguous year, and at least two distinct providers for the same identity,
   without conflict: `strong`.
4. Exact title or fuzzy title ratio at least 0.85 plus compatible author or
   year evidence: `plausible`.
5. Otherwise `weak`; empty unusable records are discarded.

Keep legacy `unavailable` readable, but new results represent availability
separately: a well-matched DOI-only record is not an arXiv import target.
Author compatibility requires a shared normalized family name and no
contradictory supplied initials for that name; it is corroboration only, never
sufficient alone. Disjoint nonempty author sets are a conflict. Different
explicit years are reported conservatively even if they may reflect editions.

Sort by confidence tier, then exact identifier match, exact title match,
compatible author match, exact year match, fuzzy title ratio, and canonical
identity key. Numeric score remains a diagnostic, not a probability: exact
identifier 8, exact title 4 (otherwise fuzzy title >=0.85: 2), compatible
author 1, exact year 1; all other factors 0. Conflict overrides score.
Assess competing candidates before `max_candidates` truncation. Persist
`total_candidate_count`, `returned_candidate_count`, `truncated` and blocking
conflict summaries so a display limit cannot turn ambiguity into eligibility.

## 7. Provider outcomes and user guidance

Keep existing providers, request limits and timeouts. Isolate malformed records
so one bad record does not discard valid siblings. Persist per-provider outcome
`ok`, `empty`, `partial`, `timeout`, `rate_limited`, `unavailable` or
`invalid_response`, with bounded, sanitized details; never expose credentials
or full request headers. Do not add retries or background calls in this release.

Use distinct boundary codes: `no_candidates`, `provider_failure`,
`partial_provider_failure`, `insufficient_metadata`, `identifier_conflict`,
`version_conflict`, `ambiguous_candidates`, `no_importable_source`.
No matches does not mean the paper does not exist; missing source does not
mean paywalled. Describe only what was observed.

Each boundary has `message`, `evidence_refs` and `next_actions`. Allowed action
codes are `review_candidates`, `provide_identifier`, `provide_local_pdf`,
`refresh_search`, `skip_reference`. These are suggestions, not scheduled work
or authorizations. Existing reports show a concise explanation and next action;
JSON exports retain full assessment. Reading a report performs no network call.

## 8. Expansion compatibility and authorization

Keep `unique_strong_v1` and its legacy query/ranking path available for existing
and explicitly requested v1 runs. Pin their resolver version to legacy v1;
do not feed v2 scores or assessments into an old policy silently.

New expansion runs default to `unique_strong_v2`, visibly stored in their
approved policy snapshot. Changing an existing run between policy versions is
not supported in this release; create a new run explicitly instead. Old runs
continue with old decisions and counters. Existing resolved targets are never
replaced by a fresh search.

v2 permits automatic selection only for one strong, conflict-free identity
with an importable arXiv source. Require exact source identity or the full
corroborated-metadata rule above. Missing providers disallow the metadata-only
corroboration route; an exact identifier may still qualify if no conflicting
evidence exists. DOI/arXiv acquisition links must be explicitly evidenced.
Retraction/withdrawal signals, unresolved version conflicts and hidden
competing identities block automation. No absence-of-retraction guarantee is
made. Direct arXiv-reference fast paths must use the same conflict checks.

Budgets, manual PDF authorization, pauses, cancellation, leases, interrupted
import reconciliation and explicit overwrite protections remain unchanged.
Search and report calls cannot import. A v2 assessment is not independent
permission to advance an expansion run.

## 9. Storage and public interface

Migrate workspace schema 8 to 9 transactionally. Add persisted resolver/schema
metadata to search runs and an assessment JSON column to candidates; keep old
columns and IDs. Legacy rows retain their original score/evidence/target and
are read as v1 with assessment absent, not synthesized as v2. Existing expansion
policy JSON without a resolver version means legacy v1.

Persist provider outcomes, parsing provenance and pre-truncation summaries in
the search snapshot. Reopening a workspace must reproduce the same assessment
without contacting providers. Migration rollback must leave schema 8 usable;
older application versions must reject schema 9 cleanly. Document backup first.

Existing search/list/resolve methods and CLI/MCP entry points stay intact.
Add optional `resolver_version` (`legacy_v1` or `deterministic_v2`) to search,
defaulting to v2. Cache reuse requires matching source/blocker, provider set,
candidate limit and resolver version. Refresh creates a new immutable snapshot;
it does not rerank or delete history. List envelopes use version 2 and may
contain explicitly versioned v1 and v2 child snapshots.

Manual resolution rejects a conflicted synthesized candidate with an actionable
error directing the caller to choose a concrete target; explicit user-supplied
resolution remains available. No new generic task-management API is added.

Suggested focused modules: `reference_query.py`, `reference_identity.py`,
`reference_assessment.py`. Integrate through `reference_search.py`, provider
adapters, Workspace serialization, expansion policy, server/CLI and reports.
Keep legacy implementation behavior isolated and regression-tested; do not
perform unrelated Workspace refactoring.

## 10. Acceptance and verification

Create an offline fixture corpus with at least 40 independently named cases,
each declaring raw reference, provider records/outcomes, expected hints,
identity groups, reason codes, confidence and automatic-selection eligibility.
Use synthetic or repository-licensed material; no private manuscripts.

Required groups include initials and punctuation; long/Unicode/TeX titles;
missing and conflicting years; DOI wrappers/case/balanced punctuation; modern
and legacy arXiv URLs/versions; shared DOI/arXiv bridge; contradictory bridges;
duplicate-provider records; same title with distinct identities; empty metadata;
malformed provider records; total and partial outages; DOI-only targets;
explicit retraction signals; ambiguity outside the returned candidate limit.

Release gates:

1. All declared fixture expectations pass; zero automatic selections in every
   negative safety case. Report numerator and denominator, not an unsupported
   real-world accuracy percentage.
2. Provider/record permutations preserve normalized output and selection.
3. Search alone performs zero imports; reports perform zero provider calls.
4. Schema-8 migration preserves historic IDs, decisions and snapshot content;
   injected migration failure rolls back; reopen reproduces v2 assessments.
5. An existing v1 expansion uses legacy behavior after upgrade; a new v2 run
   refuses conflicts and selects only eligible identities within old budgets.
6. Workspace, CLI and real MCP stdio return matching assessments and errors.
7. Full deterministic tests pass on Windows/Ubuntu and Python 3.10/3.12;
   wheel/sdist build and isolated installed-wheel CLI/MCP smoke tests pass.
8. README, walkthrough, compatibility matrix, examples and release notes show
   the policy/version boundary and schema-9 backup warning. Live provider or
   real-client smoke checks, if run, are recorded separately with date/version;
   network availability is not a deterministic test gate.

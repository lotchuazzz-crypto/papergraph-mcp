# v1.0 Formal Release Design

## Purpose

PaperGraph has reached the core product loop that motivated the project:

1. load one or more mathematical papers into a local workspace;
2. inspect extracted result, proof, citation, and source evidence;
3. start with Paper Map for one paper;
4. export durable Markdown artifacts for a single paper or a small explicit paper set;
5. preserve evidence boundaries instead of inventing hidden mathematical dependencies.

v1.0 should be a formal stabilization release, not a new research-feature release. It should make the existing v1 workflow installable, reproducible, documented, and versioned as stable.

## Product Goal

Given a new user, an MCP-capable agent, or a CLI-only reader, PaperGraph v1.0 should answer:

- how do I install or run the stable release;
- what workflow is stable enough to build around;
- which MCP tools and CLI commands are part of the v1 core;
- what durable artifacts can I export;
- which claims are evidence-backed and which are explicitly out of scope;
- how do I verify the installation before reading private papers.

## Design Choice

### Recommended Approach: Formal Release Stabilization

v1.0 should update versions, release pins, stable documentation, first-use checks, and tests. It should not add new extraction behavior, new database schema, or new MCP tools.

This is the right v1.0 shape because v0.10 through v0.13 already delivered the core reading workflow:

- v0.10: Paper Map;
- v0.11: Reading Report Export;
- v0.12: Cross-Paper Reading Plan;
- v0.13: v1.0 readiness docs and examples.

The remaining risk is not missing product surface; it is accidental instability or confusing installation/documentation.

### Rejected Alternative: Add One More Feature Before v1.0

Potential additions such as PDF rendering, symbol indexing, global paper discovery, or notation lookup are useful later, but they would widen the v1 contract and reopen design risk. They should stay post-v1 unless a later design keeps them strictly evidence-scoped and clearly tied to the reading workflow.

## Scope

### In Scope

- Release version `1.0.0`.
- Update all release pins from `0.13.0` / `v0.13.0` to `1.0.0` / `v1.0.0` in active install paths, diagnostics, CI, onboarding, tests, and README.
- Update arXiv user agent to `PaperGraph/1.0.0`.
- Update README top-level release message from v1 readiness to v1 stable.
- Add or update release documentation describing:
  - v1 stable workflow;
  - v1 public contract;
  - installation validation;
  - durable Markdown artifacts;
  - known limits and post-v1 scope;
  - release checklist for maintainers.
- Preserve and link the existing `docs/reference/v1-core-contract.md`.
- Add tests that enforce v1.0 pins, README v1 messaging, release checklist presence, and first-use command compatibility.
- Run focused tests, onboarding check, CLI command sweep, and full test suite before PR.

### Out of Scope

- New extraction logic.
- New MCP tools.
- New CLI commands.
- Database migrations.
- PDF export.
- HTML export.
- Global paper discovery.
- Semantic theorem matching.
- Notation or symbol indexing.
- Automatic external-paper import.
- Proof verification.

## Stable Contract

The v1.0 stable workflow remains the one documented in `docs/reference/v1-core-contract.md`:

1. Open or create a workspace outside the Git repository.
2. Add arXiv, local LaTeX, or born-digital PDF papers.
3. Start each paper with Paper Map.
4. Inspect proof evidence, citations, source slices, and external import plans.
5. Export a Reading Report for a single paper.
6. Export a Cross-Paper Reading Plan for a small explicit set of related papers.

v1.0 stabilizes the workflow and public command/tool names, not every internal evidence field forever. Consumers should continue to ignore unknown warning kinds gracefully.

## Versioning Requirements

Active project files should report `1.0.0`:

- `pyproject.toml`
- `uv.lock`
- runtime diagnostics and `--version`
- `src/papergraph/arxiv.py` user agent
- `.github/workflows/ci.yml` wheel smoke check
- `.github/ISSUE_TEMPLATE/bug_report.yml`
- `scripts/check_onboarding.py`
- `.agents/skills/setting-up-papergraph/SKILL.md`
- `.agents/skills/setting-up-papergraph/references/client-configuration.md`
- README pinned `uvx` commands
- version-focused tests

Historical release notes, older specs, and historical plans may keep old versions as history.

## Documentation Requirements

README should present v1.0 as the stable release, not a readiness pass. It should:

- keep the researcher-focused opening;
- show pinned `uvx --from ...@v1.0.0` commands for `--version` and `doctor`;
- keep MCP configuration examples pinned to `v1.0.0`;
- link the v1 core contract, first-workspace walkthrough, and example artifacts;
- keep evidence-boundary language;
- add a `v1.0.0` release highlight above older release highlights.

Add `docs/reference/v1-release-checklist.md` with:

- pre-release checks;
- installation validation commands;
- docs that must be updated;
- tests to run;
- GitHub release/tag expectations;
- post-v1 scope reminders.

The first-workspace walkthrough should use `v1.0.0` pinned commands and should still explain that workspace databases belong outside the Git repository.

## Compatibility Requirements

v1.0 should remain compatible with:

- Python `>=3.10`;
- current dependency constraints in `pyproject.toml`;
- Windows and Ubuntu CI matrix already used by the project;
- MCP clients that can launch stdio servers through `uvx`;
- CLI-only users who do not install a global `papergraph-mcp` executable.

README CLI examples must match current `argparse` syntax: command name first, then command-specific options such as `--workspace`, `--paper-id`, `--result-id`, `--queue-id`, and `--session-id`.

## Testing Requirements

Tests should cover:

- repository metadata version is `1.0.0`;
- lockfile package version is `1.0.0`;
- runtime diagnostics report `version: 1.0.0` and `release_tag: v1.0.0`;
- `papergraph-mcp --version` prints `papergraph-mcp 1.0.0`;
- README active install pins use `v1.0.0`;
- onboarding skill active pins use `v1.0.0`;
- first-workspace walkthrough uses pinned `v1.0.0` commands;
- v1 release checklist exists and contains concrete checks;
- README CLI examples do not use the obsolete `papergraph-mcp --workspace ... <command>` form.

Before PR:

```powershell
uv run pytest tests\test_repository.py tests\test_cli.py tests\test_diagnostics.py tests\test_server.py tests\test_onboarding.py tests\test_v1_readiness_docs.py -q -p no:cacheprovider --basetemp .pytest-tmp
```

Run a CLI command sweep over README-listed commands:

```powershell
uv run papergraph-mcp <command> --help
```

Run the full suite:

```powershell
uv run pytest -q -p no:cacheprovider --basetemp .pytest-tmp
```

## Release Notes Shape

v1.0 release notes should emphasize:

- stable evidence-first reading workflow;
- Paper Map, Reading Report, and Cross-Paper Reading Plan;
- local SQLite workspaces;
- deterministic Markdown artifacts;
- MCP and CLI usage;
- explicit evidence boundaries.

They should avoid claiming proof verification, automatic literature review, semantic theorem equivalence, or global discovery.

## Acceptance Criteria

v1.0 is ready to merge when:

- active version pins are consistently `1.0.0` / `v1.0.0`;
- README and onboarding commands are copyable for first-time users;
- v1 release checklist exists and is linked or discoverable from README or reference docs;
- focused tests pass;
- onboarding script reports `ready_for_smoke_test: true` in a normal local environment;
- CLI command sweep succeeds for documented commands;
- full test suite passes;
- PR is created against `main`.

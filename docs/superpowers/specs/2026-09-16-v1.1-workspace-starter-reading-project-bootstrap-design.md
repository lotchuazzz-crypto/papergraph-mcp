# v1.1 Workspace Starter / Reading Project Bootstrap Design

## Context

PaperGraph v1.0.0 stabilized the evidence-first reading core: local workspaces, Paper Map, Reading Report, Cross-Paper Reading Plan, proof/citation evidence, reading queues, reading sessions, and explicit evidence boundaries.

The v1 release handoff is `D:/ai4math/papergraph-mcp/.worktrees/design-v0.12-cross-paper-reading-plans/docs/sessions/260916-111126-v1-release-handoff.md`. It records that v1.0.0 was merged into `main`, tagged, and published as a GitHub Release from commit `5e6194f`, with final verification at `461 passed, 1 skipped`. It recommends v1.1 Workspace Starter / Reading Project Bootstrap as the strongest next feature direction.

The next product gap is first-project ergonomics. v1.0 tells a user which commands exist, but a researcher still has to manually choose a workspace path, load one or more papers, run Paper Map, decide which artifacts to export, and preserve exact follow-up commands. v1.1 should turn that stable workflow into a guided bootstrap for a new reading project without changing extraction semantics.

## Product Goal

Given a fresh researcher or an agent acting for one, PaperGraph v1.1 should create a usable local reading project from a small explicit set of paper inputs and produce a deterministic starter package:

- workspace opened or initialized outside the repository;
- papers loaded from arXiv, local LaTeX, or born-digital PDF inputs;
- Paper Map generated for every loaded paper;
- Reading Report exported for each usable paper;
- Cross-Paper Reading Plan exported when two or more papers are present;
- optional reading queue and reading session created for a selected target result when the user asks for stateful reading setup;
- one starter Markdown file explaining what was created, what evidence is sparse, and what to do next;
- one machine-readable manifest with exact commands, artifact paths, loaded paper IDs, and evidence-quality warnings.

The feature is a workflow bootstrapper, not a new inference engine. It must not discover papers globally, auto-import external papers, infer theorem equivalence, verify proofs, or hide evidence limits.

## Users

- A researcher starting a new paper-reading project.
- An MCP-capable coding or research agent setting up PaperGraph for a user.
- A CLI-only user who wants one reproducible command to create starter artifacts.
- A future session handoff that needs a compact project state rather than scattered command outputs.

## Design Principles

- **Compose stable v1 tools:** v1.1 should orchestrate `open_workspace`, paper import, Paper Map, report export, cross-paper plan export, and optionally reading queue/session creation.
- **Explicit inputs only:** all papers come from user-provided arXiv requests, local paths, or PDF paths.
- **Dry-run first:** agents and users should be able to preview the plan before writing a workspace or artifacts.
- **Filesystem-safe by default:** generated files go under a user-specified project directory or an explicit output directory; PaperGraph never writes into the Git repository unless the user points there.
- **Evidence boundaries remain visible:** starter output must surface sparse evidence, unresolved references, and external import risks instead of making the project look complete.
- **Deterministic artifacts:** no timestamps, random IDs, or machine-specific absolute paths in Markdown content unless supplied as a CLI output path in a JSON status envelope.

## Approaches Considered

### Option 1: Documentation-Only Starter

Add a richer walkthrough with copyable command blocks and examples.

This is low risk, but v1.0 already has a first-workspace walkthrough. Documentation alone does not reduce the number of manual steps and does not give agents a single contract for safe setup.

### Option 2: Agent Prompt / Skill Only

Add an onboarding prompt or repository skill that tells a coding agent how to run the v1 workflow.

This helps MCP users but leaves CLI-only users behind. It also makes the workflow depend on agent behavior rather than a stable PaperGraph API. A skill can wrap v1.1 later, but the core bootstrap should live in PaperGraph.

### Option 3: First-Class Workspace Starter

Add a read/write workspace bootstrap API plus MCP and CLI wrappers. It accepts explicit paper inputs, validates the planned actions, then creates starter artifacts from existing v1 tools.

This is the recommended v1.1 route. It is useful immediately, keeps behavior evidence-first, and gives agents a small stable surface to call for first-project setup.

## Scope

### In Scope

Add a new project bootstrap module that supports:

- planning a starter run without writing anything;
- creating or opening a workspace at an explicit path;
- loading explicit paper inputs:
  - arXiv raw request strings, URLs, Markdown links, or IDs through existing arXiv validation;
  - local LaTeX root files with explicit `paper_id`;
  - local PDF files with explicit `paper_id`;
- generating Paper Map payloads for loaded papers;
- exporting Markdown Reading Reports to an artifact directory;
- exporting one Cross-Paper Reading Plan when two or more papers are loaded;
- optionally selecting a target result and creating a reading queue plus reading session when requested;
- writing a starter Markdown file summarizing the project state and next commands;
- writing a JSON manifest with exact commands and artifact paths;
- returning a structured JSON payload for MCP/CLI consumers.

Add MCP tools:

```python
workspace_plan_starter_project(...)
workspace_bootstrap_reading_project(...)
```

Add CLI commands:

```powershell
papergraph-mcp plan-starter-project ...
papergraph-mcp bootstrap-reading-project ...
```

Update README, first-workspace walkthrough, v1 core contract, examples, and tests.

### Out of Scope

- New extraction logic.
- New database schema.
- New theorem matching, symbol indexing, or notation indexing.
- Global paper discovery.
- Automatic external-paper import.
- Network calls beyond user-requested arXiv loads.
- PDF/HTML rendering.
- LLM-authored mathematical explanation.
- Proof checking.
- Creating parent directories silently outside the explicit project or artifact directory.

## Public Model

### Input Shape

The internal Python API should accept a typed or validated dict equivalent to:

```python
{
    "workspace_path": "C:/Users/me/papergraph-projects/xiao/workspace.sqlite3",
    "artifact_dir": "C:/Users/me/papergraph-projects/xiao/artifacts",
    "project_title": "Xiao conjecture reading project",
    "papers": [
        {"kind": "arxiv", "input": "2401.12345", "main_file": None, "refresh": False},
        {"kind": "local_tex", "path": "D:/papers/paper-a/main.tex", "paper_id": "local:paper-a"},
        {"kind": "pdf", "path": "D:/papers/paper-b.pdf", "paper_id": "local:paper-b"}
    ],
    "focus": "slope inequality",
    "target_result_id": None,
    "create_queue": True,
    "create_session": True,
    "max_candidates": 5,
    "dry_run": False
}
```

Validation rules:

- `workspace_path` is required and must point to a file path, not a directory.
- `artifact_dir` is required for bootstrap and optional for plan-only mode.
- `papers` must contain between one and eight inputs.
- `local_tex` and `pdf` inputs require explicit `paper_id`.
- arXiv inputs use existing `validate_arxiv_request`; conflicts stop the plan with `action: ask_user_to_choose`.
- `focus` may be `None` or a trimmed non-empty string.
- `target_result_id` may be omitted; if omitted and queue/session creation is requested, use the top Paper Map candidate only when evidence status is usable and the candidate is explicit.
- `max_candidates` follows Paper Map validation.
- duplicate planned paper IDs fail before writing.

### Plan Payload

`plan_starter_project(...)` returns:

```python
{
    "starter_schema_version": 1,
    "status": "ready" | "blocked",
    "action": "bootstrap_reading_project" | "ask_user_to_choose" | "inspect_error",
    "workspace_path": "...",
    "artifact_dir": "...",
    "project_title": "...",
    "paper_inputs": [...],
    "planned_papers": [...],
    "planned_artifacts": [
        {"kind": "starter_summary", "path": "START_HERE.md"},
        {"kind": "starter_manifest", "path": "papergraph-starter-manifest.json"},
        {"kind": "reading_report", "paper_id": "...", "path": "..."},
        {"kind": "cross_paper_reading_plan", "path": "..."}
    ],
    "planned_state_changes": [
        {"kind": "open_workspace", "path": "..."},
        {"kind": "add_paper", "paper_id": "..."},
        {"kind": "create_reading_queue", "target_result_id": "..."},
        {"kind": "create_reading_session", "paper_id": "..."}
    ],
    "warnings": [...],
    "blocking_issues": [...]
}
```

Plan-only mode does not open SQLite, import papers, write artifacts, or create directories. It may validate paths and arXiv request syntax.

### Bootstrap Payload

`bootstrap_reading_project(...)` returns:

```python
{
    "starter_schema_version": 1,
    "status": "written" | "partial" | "blocked",
    "workspace": {"path": "...", "schema_version": 4, "paper_count": 2},
    "papers": [...],
    "paper_maps": [...],
    "artifacts": [
        {"kind": "starter_summary", "path": "...", "bytes": 1234},
        {"kind": "starter_manifest", "path": "...", "bytes": 1234},
        {"kind": "reading_report", "paper_id": "...", "path": "...", "bytes": 2345},
        {"kind": "cross_paper_reading_plan", "path": "...", "bytes": 3456}
    ],
    "reading_queue": {...} | None,
    "reading_session": {...} | None,
    "warnings": [...],
    "next_commands": [...]
}
```

`partial` means at least one paper or artifact was created and at least one non-fatal paper failed. Fatal validation failures return `blocked` before writes.

## MCP Tools

Add:

```python
workspace_plan_starter_project(
    workspace_path: str,
    artifact_dir: str | None,
    papers: list[dict],
    project_title: str | None = None,
    focus: str | None = None,
    target_result_id: str | None = None,
    create_queue: bool = True,
    create_session: bool = True,
    max_candidates: int = 5,
) -> dict
```

and:

```python
workspace_bootstrap_reading_project(
    workspace_path: str,
    artifact_dir: str,
    papers: list[dict],
    project_title: str | None = None,
    focus: str | None = None,
    target_result_id: str | None = None,
    create_queue: bool = True,
    create_session: bool = True,
    max_candidates: int = 5,
) -> dict
```

These tools should not require a previously opened workspace. They open the target workspace internally and, after a successful bootstrap, make it the active MCP workspace so follow-up calls can continue naturally.

## CLI

Add a conservative JSON-friendly CLI:

```powershell
papergraph-mcp plan-starter-project `
  --workspace C:/Users/me/papergraph-projects/xiao/workspace.sqlite3 `
  --artifact-dir C:/Users/me/papergraph-projects/xiao/artifacts `
  --project-title "Xiao conjecture reading project" `
  --arxiv "2401.12345" `
  --pdf D:/papers/tan-liu.pdf=local:tan-liu `
  --focus "slope inequality"
```

```powershell
papergraph-mcp bootstrap-reading-project `
  --workspace C:/Users/me/papergraph-projects/xiao/workspace.sqlite3 `
  --artifact-dir C:/Users/me/papergraph-projects/xiao/artifacts `
  --project-title "Xiao conjecture reading project" `
  --arxiv "2401.12345" `
  --tex D:/papers/paper-a/main.tex=local:paper-a `
  --pdf D:/papers/paper-b.pdf=local:paper-b `
  --focus "slope inequality"
```

CLI rules:

- `--arxiv` may repeat and accepts the same raw input as `load-arxiv-request`.
- `--tex PATH=PAPER_ID` may repeat.
- `--pdf PATH=PAPER_ID` may repeat.
- `--no-queue` disables queue creation.
- `--no-session` disables session creation.
- `--target-result-id` overrides automatic target selection.
- `plan-starter-project` prints JSON only.
- `bootstrap-reading-project` writes artifacts and prints JSON status only.
- Bootstrap always writes both `START_HERE.md` and `papergraph-starter-manifest.json`.
- Existing artifact files are overwritten only with `--overwrite`; otherwise the command fails before writes.
- The command may create `artifact_dir` only when the user supplied that exact directory.

## Starter Markdown

Write `START_HERE.md` under the artifact directory. Stable headings:

```markdown
# PaperGraph Reading Project: <project title>

## Project

## Papers Loaded

## Start Here

## Reading Artifacts

## Reading Queue And Session

## Evidence Quality

## External Reading Risks

## Evidence Boundaries

## Next Commands
```

Content rules:

- Include workspace path only as the user supplied it in CLI/MCP input.
- List every loaded paper with title, source type, evidence status, result/proof/citation counts, and recommended start result when available.
- Put the strongest next action under `Start Here`: open Paper Map, read the top Reading Report, inspect Cross-Paper Reading Plan, or resolve a blocking issue.
- Link generated Markdown artifacts by relative path from `artifact_dir`.
- Include warnings for sparse or limited papers.
- Include external risks from Paper Map and Cross-Paper Reading Plan.
- Always include evidence boundaries from the v1 core contract.

## Starter Manifest

Write `papergraph-starter-manifest.json` under the artifact directory. The manifest is the durable handoff object for agents and later sessions:

```json
{
  "starter_schema_version": 1,
  "workspace_path": "...",
  "artifact_dir": "...",
  "project_title": "...",
  "paper_ids": ["arxiv:2401.12345", "local:paper-a"],
  "artifacts": [
    {"kind": "starter_summary", "path": "START_HERE.md"},
    {"kind": "reading_report", "paper_id": "arxiv:2401.12345", "path": "arxiv-2401-12345-reading-report.md"},
    {"kind": "cross_paper_reading_plan", "path": "cross-paper-reading-plan.md"}
  ],
  "next_commands": [
    "papergraph-mcp get-paper-map --workspace C:/Users/me/papergraph-projects/xiao/workspace.sqlite3 --paper-id arxiv:2401.12345"
  ],
  "warnings": []
}
```

The manifest should use paths relative to `artifact_dir` for generated artifacts and preserve the user-supplied workspace path in commands. It must not include timestamps or environment-derived absolute paths other than paths the user supplied.

## Architecture

Create:

```text
src/papergraph/starter.py
```

Responsibilities:

- input normalization and validation;
- arXiv request planning through existing validators;
- safe artifact-path planning;
- orchestration of workspace imports and existing report exporters;
- automatic target-result selection from Paper Map;
- deterministic starter Markdown rendering;
- deterministic starter manifest rendering;
- structured payload assembly.

`Workspace` should expose thin methods:

```python
def plan_starter_project(...): ...
def bootstrap_reading_project(...): ...
```

`server.py` should only handle MCP/CLI argument conversion and error envelopes. It should not contain bootstrap orchestration or Markdown rendering logic.

No schema migration is required. Reading queue/session creation uses existing workspace tables.

## Data Flow

1. Normalize input papers and validate counts.
2. Validate workspace path and artifact paths.
3. Validate arXiv requests. Stop on ambiguity before writing.
4. Build a starter plan with paper IDs, artifact paths, and intended state changes.
5. For bootstrap, create the artifact directory if explicitly supplied and absent.
6. Open or create the workspace.
7. Import each paper through existing workspace import paths.
8. Generate Paper Map for each imported paper.
9. Export per-paper Reading Reports.
10. Export Cross-Paper Reading Plan when at least two papers loaded.
11. Select target result from explicit input or top usable Paper Map candidate.
12. Create reading queue/session if requested and supported by evidence.
13. Render `START_HERE.md`.
14. Render `papergraph-starter-manifest.json`.
15. Return structured status with warnings and next commands.

## Error Handling

- Ambiguous arXiv input returns `status: blocked`, `action: ask_user_to_choose`, and no writes.
- Duplicate paper IDs fail before writes.
- Existing artifact files fail before writes unless `overwrite=True`.
- Unknown target result fails before queue/session creation.
- A single paper import failure may produce `partial` only after earlier papers were already imported; the payload must list failed inputs and successful artifacts.
- Artifact write failure returns a JSON error and closes the workspace cleanly.
- Sparse evidence never fails bootstrap; it appears as a warning.

## Testing

Add focused tests for:

- plan payload contains planned papers, artifacts, state changes, and warnings without writing files;
- arXiv conflict blocks before writes;
- duplicate paper IDs block before writes;
- local TeX and PDF input parsing require explicit IDs;
- bootstrap creates a workspace and starter artifacts for one paper;
- bootstrap creates per-paper reports and a cross-paper plan for two or more papers;
- `START_HERE.md` contains all required headings and evidence boundaries;
- `papergraph-starter-manifest.json` contains exact artifact paths and next commands without timestamps;
- automatic target selection uses top usable Paper Map candidate and is deterministic;
- `--no-queue` and `--no-session` suppress state creation;
- existing artifacts fail without overwrite;
- partial import failures are reported without hiding successful imports;
- MCP tools return structured payloads and convert errors to `ToolError`;
- CLI plan prints JSON only;
- CLI bootstrap writes artifacts and prints JSON status;
- README and walkthrough mention the v1.1 starter workflow.

## Release Notes Shape

Release as `v1.1.0`.

Release notes should emphasize:

- one-command reading project bootstrap;
- dry-run planning before writes;
- generated `START_HERE.md`, `papergraph-starter-manifest.json`, Reading Reports, and Cross-Paper Reading Plan;
- optional reading queue/session creation;

## Acceptance Criteria

v1.1 is ready when:

- starter planning works without writing files;
- bootstrap creates a usable workspace and deterministic artifacts from explicit inputs;
- ambiguous arXiv requests and unsafe artifact overwrites stop before writes;
- generated starter Markdown is researcher-readable and includes evidence boundaries;
- generated manifest preserves exact commands and artifact paths for later handoff;
- queue/session creation composes existing workspace state without schema changes;
- README and first-workspace docs show the starter path;
- focused tests and full suite pass;
- PR is created against `main`.

# PaperGraph v0.4.2 First-Use Hardening Design

## Goal

Make PaperGraph's first real-paper experience harder to misread. v0.4.2 should keep the existing conservative, evidence-first architecture while adding clear diagnostics, friendlier theorem-kind metadata, and onboarding guardrails for common first-use mistakes.

This release is a hardening release. It does not add proof attachment, semantic dependency inference, theorem equivalence detection, automatic cited-paper import, or LLM-based mathematical judgment.

## Triggering Incident

A simulated first-time user asked an agent to clone PaperGraph MCP and analyze an arXiv paper. The prompt contained a conflicting identifier pair: text `math/0307200`, but the Markdown link pointed to `https://arxiv.org/abs/2609.01574`.

The agent used PaperGraph successfully and avoided inventing dependencies. It listed seven theorem-like nodes and selected `classification` as the likely main theorem. However, PaperGraph returned empty dependencies as a bare list, and the answer did not clearly distinguish "no explicit theorem-label references detected" from "no mathematical dependencies exist."

The response was technically grounded but too thin for a research tool. The tool exposed data, not enough interpretive boundary information.

## User Experience Requirements

When a user first asks PaperGraph to analyze a real arXiv paper, the agent should be able to produce a grounded answer with these properties:

1. It detects an arXiv ID versus arXiv URL mismatch before loading the wrong paper and asks the user to choose one.
2. It reports theorem-like environments in human-readable categories even when the raw LaTeX environment is abbreviated, such as `thm`.
3. It states the basis for dependency results: in v0.4.2, dependencies are extracted from explicit LaTeX references inside theorem-like statements only.
4. It treats an empty dependency list as a scoped negative result, not as evidence of mathematical independence.
5. It exposes unresolved references and parser limitations directly enough that an agent does not need to guess why a graph is sparse.
6. It preserves existing evidence-first discipline: when PaperGraph does not support a claim, the answer must say so rather than fill the gap.

## Scope

### In Scope

- Version and documentation consistency for the v0.4.2 release line.
- A first-use guardrail in onboarding and reusable prompt text for conflicting arXiv IDs and URLs.
- Theorem environment metadata with raw kind, display kind, and normalized kind.
- Dependency diagnostics for single-paper and workspace dependency tools.
- README guidance explaining what empty dependencies mean in the current release.
- Tests using synthetic fixtures plus the existing `math/0307200` documented scenario where feasible without relying on live arXiv downloads.

### Out of Scope

- Parsing `proof` environments and attaching proofs to theorem nodes.
- Extracting dependencies from prose references such as "the previous theorem."
- Ranking or proving the main theorem.
- Inferring semantic equivalence between theorem statements.
- Downloading or importing cited papers automatically.
- Changing the SQLite schema in a way that requires migration support, unless implementation shows that the metadata cannot be added compatibly.

## Theorem Kind Metadata

The parser currently treats the LaTeX environment name as the kind. For example, `\newtheorem{thm}{Theorem}` produces `kind: "thm"`, even though a human expects "Theorem."

v0.4.2 should preserve the raw environment name while adding friendlier metadata:

- `raw_kind`: the exact LaTeX environment name, such as `thm`.
- `display_kind`: the display name declared by `\newtheorem`, such as `Theorem`; defaults to the raw environment when no display name is known.
- `normalized_kind`: a lowercase semantic category when safely recognized, such as `theorem`, `lemma`, `proposition`, `corollary`, `definition`, `claim`, or `conjecture`; otherwise the lowercased raw environment.

For compatibility, existing `kind` should remain present. In v0.4.2 it should continue to behave as the raw environment name unless there is a deliberate compatibility decision to change it. New user-facing summaries should prefer `display_kind` and `normalized_kind`.

## Dependency Diagnostics

Dependency APIs should continue returning dependency nodes, but the agent also needs structured diagnostics. The implementation may use a companion field or companion tool, but the final MCP shape must let an agent answer:

- Which theorem was queried?
- Was the result direct or recursive?
- Which references were found in the queried theorem's statement?
- Which references resolved to theorem-like nodes?
- Which references did not resolve?
- What extraction basis was used?
- What warning should accompany an empty result?

The required extraction basis string for v0.4.2 is:

```text
statement_explicit_latex_refs_only
```

When dependencies are empty, diagnostics must include a warning equivalent to:

```text
No explicit theorem-label dependencies were detected in the theorem statement. This is not evidence that the theorem has no mathematical dependencies.
```

Workspace dependency diagnostics should use the same meaning, with global theorem IDs.

## First-Use Guardrails

The repository-local onboarding skill and reusable prompt should teach agents to check arXiv identifiers before loading:

- If a user provides both an arXiv ID and an arXiv URL, compare the normalized IDs.
- If they differ, stop and ask which one to analyze.
- Do not silently prefer the text ID, the URL ID, or the newest-looking ID.
- If only one ID is present, proceed with that ID after normalization.

The guardrail belongs in user-facing setup material because it shapes agent behavior before PaperGraph receives a tool call.

## README Updates

The README should be explicit about the current boundary:

- PaperGraph v0.4.2 dependency traversal follows explicit LaTeX references between theorem-like statements.
- Empty dependency results mean that PaperGraph found no resolvable theorem-label references under that rule.
- Empty dependency results do not prove mathematical independence.
- Proof parsing and prose dependency extraction are future work.
- The `math/0307200` compact check should demonstrate this boundary rather than accidentally overpromising.

## Testing Strategy

Development must follow test-driven changes:

1. Add parser tests showing `\newtheorem{thm}{Theorem}` yields raw, display, and normalized kind metadata.
2. Add summary/full serialization tests preserving old `kind` while exposing new metadata.
3. Add dependency diagnostic tests for non-empty, empty, recursive, and unresolved-reference cases.
4. Add workspace dependency diagnostic tests if workspace APIs expose the new diagnostic structure.
5. Add onboarding/README tests for arXiv ID and URL mismatch guardrails.
6. Run the targeted tests red before implementation, then green after implementation.
7. Run the full suite before claiming completion.

Tests must not depend on live arXiv network access. If a real-paper regression is added for `math/0307200`, use checked-in source excerpts or a recorded synthetic fixture that captures the relevant parser shape.

## Release Boundaries

This hardening should start from the validated v0.4.1 release state, not from the stale primary checkout. Development should happen on a fresh branch from the isolated v0.4.1 worktree.

The release target is v0.4.2. Do not push branches, open pull requests, create tags, publish releases, or delete old branches without explicit user approval.

## Future Direction

After v0.4.2, the natural v0.5 theme is proof-aware dependency extraction:

- Attach theorem statements to adjacent proof environments.
- Mark dependency source as statement, proof, citation, or unresolved prose cue.
- Add main theorem candidate ranking with evidence and confidence, not absolute claims.
- Build real-paper regression cases from public arXiv sources.
- Keep provenance visible at every step so stronger analysis does not weaken trust.
